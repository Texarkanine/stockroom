# Milestones: warehouse-file-growth

## Cross-milestone invariants & constraints

Spec: [issue 147](https://github.com/Texarkanine/stockroom/issues/147), as amended by the operator decisions in `memory-bank/active/projectbrief.md`. The 2026-10-21 decision to drop the HNSW index replaces the issue's "keep HNSW" and every requirement built on it. The 2026-10-22 decision merges the swap into the check: each machine first records a verified rehearsal and swaps at a later session start. [Issue 146](https://github.com/Texarkanine/stockroom/issues/146) is out of scope. The 2026-10-22 rulings on migrations replace every earlier statement that edits a released migration or treats the copy chain as short-lived: released migrations are immutable, one chain plus a frozen schema file creates new warehouses, a warehouse migrates or stops, and the copy-and-swap is durable.

No vector index (operator, 2026-10-21): the HNSW index and the `vss` extension leave the engine. After the first milestone, nothing in the engine loads or installs `vss`, creates a vector index, or sets an HNSW setting. Semantic search ranks every embedding exactly. Migration `0009` drops the index where one exists. The released `0003`, which creates the index and needs `vss`, keeps its released SQL (operator, 2026-10-22). New warehouses are created from the schema file and never run it, and a warehouse that would have to run it stops with an error (see "Migrate or stop"). No milestone adds a vector index back. That door stays open to a later project, which would bring the index back with a rebuild routine. Measured 2026-10-21 on copies of this machine's warehouse (133,793 vectors), where the index returned 37 to 65 rows for a top-100 search in 34 ms:
- Exact search that keeps the nearest chunk per message owner and cuts to the limit before it joins `messages` takes 153 ms (median) on DuckDB 2.0.0 and 205 ms on 1.5.4, and always returns the full limit. Today's scoped SQL, which joins first and dedups with `QUALIFY row_number()`, takes 1,321 ms and 1,745 ms run with no scope.
- Dropping the index and checkpointing took 0.8 s and cut used blocks from 161,453 to 6,846 (256 KiB each), freeing 37.4 GiB inside the 39.5 GiB file.

DuckDB 2.0.0's replay bug lives in `vss`: replaying a `.wal` that holds inserts into an HNSW-indexed table breaks the index. With `vss` never loaded, it cannot reach a stockroom warehouse. Measured on DuckDB 1.5.4 and 2.0.0, both with extension autoload off and with DuckDB's default autoload and autoinstall settings: DuckDB never loads `vss` by itself for a file that has the index. Such a file, with or without a leftover `.wal` from a killed 1.5.4 embed, opens read-only and read-write and keeps every row. It answers an exact cosine query, drops the index inside a transaction, accepts an insert, and checkpoints with no `.wal` left. On 2.0.0 without `vss`, `COPY FROM DATABASE` from a file that still has the index fails ("unknown index type 'HNSW'"), so nothing copies a file before it has migrated.

Migrations (operator, 2026-10-22): a migration that shipped in a release never has its SQL changed to do something materially different. Comments may be added or changed; #128 added `@rel` lines to the released `0001` and `0007`, and later ERD edges can go into migrations the same way. A gate in `make ci` and CI fails when a migration file in the latest release tag has different SQL in the working tree, compared with comments and whitespace removed. Milestone 3 adds it, and the CI checkout fetches tags. One chain runs forever. New warehouses are created from a frozen schema file pinned to one chain version, version 9 in this project. It holds that version's tables, columns, keys, and the `session_token_usage` view, no index, and zstd on `messages.text` and `tool_calls.tool_input`. A new warehouse records one `schema_version` row naming the schema file, then migrates forward through any later migrations. A schema file is frozen like a migration; a newer one would be a new file at a later version. A test keeps a warehouse built from the schema file equal to one built by the chain at that version, apart from compression. No runner rule may record a version without running it. The format boundary is a named schema version next to the storage version: 9 in this project, where it equals the head. The check's precondition is "at the format boundary", not "at the head". This project adds no migration after `0009`. A later release that adds one must also make the runner stop an old-format warehouse at the boundary with an error until the copy-and-swap has converted it, because old-format warehouses run the chain only up to that boundary. That release also decides how long phase B's wait may hold such a warehouse.

Migrate or stop (operator, 2026-10-22): a warehouse that cannot reach the head stops in an error state that names the file and the remedy, which users discover and must resolve. Code after the DuckDB 2.0 point never detects an older, unmigrated state and copes with it, so it has no degraded modes.

Durability (operator, 2026-10-22, replacing the 2026-10-21 lifetime rule): old-format warehouses may not persist. A warehouse runs the chain to the format boundary, and the copy-and-swap then moves it to the new format. So milestones 5 to 7 (the verified copy, the check with its swap, and the session-start launch) are the v1-to-v2 step of the chain and durable code with normal care, even with about five installs today. In this project the head and the boundary are both 9, so nothing forces a conversion yet: a skip retries at the next session start and has no error state of its own (operator, 2026-10-22). Take the simpler option whenever it cannot lose a warehouse. The data-safety rules below do not relax. Keep the chain in its own module, touching shared code only at its entry point, the hook command, and doctor's check line.

DuckDB (operator, 2026-10-21): the engine moves to DuckDB 2.0, a long-term support line supported until at least October 2027 (the 1.5 line ends in March 2027). New files and the copy use storage `v2.0.0`. The operator chose it over `v1.5.0`, which DuckDB 1.5.4 could still open. DuckDB before 2.0 cannot open a file that 2.0 creates. Later milestones stay on the 2.0 line; a 2.0 patch bump is fine. DuckDB behaviour stated below was measured on 2.0.0 on 2026-10-21 unless it says otherwise.

Releases (operator, 2026-10-21, "time to ship something"; amended 2026-10-22): milestones 1, 2, and 3 make the first release. Restoring the released `0003` breaks new installs until milestone 3's schema-file path exists, so they ship together, and milestone 1 no longer ships alone. Later milestones ship in later releases. The swap reaches users with the session-start launch in milestone 7. No release carries the 2.0 lock with a vector index or `vss`. Before a release that carries the 2.0 lock, the operator runs the shadow test from a clone of the branch on the personal Mac, not the work Mac. It passed on 2026-10-22 against `ce16489` (milestones 1 and 2). It passed again on Puck on 2026-10-23 against `09ea4ae`, after milestone 3 had landed: exit 0 in 43s, and the copy stayed `v1.0.0+`. Figures are in `progress.md`. The milestone 1 to 3 pull request opens only after milestone 3 restores the released migrations. A branch clone runs only that test there, never `make shim`, so the branch does not become the live engine on a Mac. This machine is different. Its live `stockroom` shim runs this checkout, the 03:30 nightly job uses that shim, and the commit hook syncs this checkout's environment to its working-tree lock on every commit. So any commit on this branch is live here at the next run. The first commit that contains milestone 1's migration drops the index on this machine's warehouse, and the 2.0 lock is the last change milestone 2 brings into this checkout.

Skipped releases (operator, 2026-10-21): users skip releases, so every release must stand alone. A user who arrives from any earlier stockroom release, with no release in between, gets a warehouse that opens, migrates forward, and works, or that stops with an error saying what to do when it cannot reach the head (see "Migrate or stop"). No milestone may assume that a user ran an earlier milestone's release or the check. Every tagged release so far (v0.1.0 to v2.1.3) pinned DuckDB 1.5.4. v0.1.0 shipped `0001` to `0004` together, and every release loaded `vss` before migrating. So a release must handle each of these arrivals:
- a `v1.0.0+` file at schema 3 to 8, with the HNSW index. Every warehouse with rows is at schema 4 or higher. It migrates to the head without `vss`, and `0009` drops the index;
- such a file with a `.wal` left by a 1.5.4 embed that was killed before the user updated;
- a `v1.0.0+` file below schema 3: the empty file a failed first open left behind (for example, when `ensure_vss` could not reach the network), or a crash partway through a first open. It holds no rows. It would need the released `0003`, and so `vss`, so it stops with an error that names the file and tells the user to move it aside;
- a `v2.0.0+` file that a release of this project created. Milestones 1 to 3 ship together, so a release always builds one from the schema file, with zstd. A `v2.0.0+` file without zstd comes only from branch testing;
- no warehouse at all.

Tests that need an old file create it at storage `v1.0.0` with the packaged chain, which is the released chain, loading `vss` for `0003` in a separate process. A test that needs the index creates it with `vss` loaded only in a separate process, or closes every such connection before the engine opens the file. Connections to the same path in one Python process share one DuckDB database and the extensions loaded in it. Nothing outside tests loads `vss`.

"Zstd on a column" is read from that column's data segments in `pragma_storage_info`: `VARCHAR` for `messages.text` and `JSON` for `tool_calls.tool_input`. Validity segments under the same column name show `Uncompressed` or `Constant` even when zstd is on, so they do not count. A table with no rows has no data segments; each check that reads zstd states what it does with an empty table.

No milestone deletes the original warehouse file or a backup. A rewrite attaches the original `READ_ONLY` and never opens it for writing. The only replace of the live path is phase B of the check pass. It replaces the file only with a copy that the same run built and verified, and only after a verified rehearsal of the same check version on that machine at least one day earlier.

The storage upgrade stays outside `schema_version`. No milestone adds a migration that rebuilds populated `messages` or `tool_calls`. The index-drop migration drops an index and rebuilds no table. A skipped or absent rewrite must not make `open_current()` treat the warehouse as behind head.

This project does not quantize vectors, tier history out, add a `compact` subcommand, or chase the primary-key leak in code.

Doctor (operator, 2026-10-21): a user can run any discoverable doctor command with full confidence that nothing is written. `probe` and `smoke` never write. Any doctor action that writes sits behind `stockroom doctor fix <name>` and runs only when the user names it. This project adds no doctor fix. Readers and doctor never start a rewrite.

The check pass (operator, 2026-10-22) runs in two phases recorded in one check record per machine. Phase A, the rehearsal, builds a copy, verifies it, records `rehearsed` with its measurements, deletes the copy, and does not swap. Phase B runs at a later session start, at least one day after a `rehearsed` record of the same check version. It copies the warehouse again as it is that day, verifies again, hard-links the original to the backup name, and replaces the live file. The session-start hook starts the pass detached, through an internal engine entry point that the user guide does not list, and session start does not wait for it. "No new CLI command" means no new user-facing command. Nothing else starts the pass: not Cursor's `beforeSubmitPrompt` hook, ingest, embed, `migrate`, `backfill`, or any other writer open, not readers or the dashboard, not `doctor`, and not the nightly job.

Swapped, verification mismatch, already new, a crash, and a time-limit overrun are final for a check version, and later session starts do nothing. `rehearsed` is not final; it waits for phase B. A crash or an overrun stays in the record for doctor to show, and deleting the record file runs the check again from phase A. Skips build nothing and are not final, so the next session start tries again. The skip reasons are low disk, a wal, a busy flock, a read-only filesystem, no warehouse yet, and a warehouse below the format boundary. A filesystem that refuses hard links is out of scope (operator, 2026-10-22): APFS, Mac OS Extended (Journaled), ext4, and NTFS all support them. The record names the check version, so a later release that changes the check runs it again. A release that changes the check version and keeps phase B off is the kill switch.

After it, nothing in the engine, its tests, its docs, or `memory-bank` system patterns and tech context describes a vector index as present. - The new-file milestone owns:
  - the restoration of released migrations and the immutability gate;
  - the explicit storage setting and the format-boundary constant;
  - the frozen schema file, with its ZSTD clauses on `messages.text` and `tool_calls.tool_input`;
  - the new-warehouse creation path, which builds a warehouse file under a temp name and renames it into place when complete.

  The copy milestone extends that same builder to copy rows from an original, and does not restate the schema.
- The doctor milestone owns the storage section of the doctor report, the live-size estimate, and the backup filename. The check milestone owns the check record, adds one line for it to that section, uses the live-size estimate for its low-disk test, and writes the backup under that filename. It does not add a second report. The record is a sidecar file under the stockroom home. Nothing writes the check result into the warehouse.
- The copy milestone owns equality and catalog verification, and the measurements the builder returns. The check milestone calls that builder in both phases and stores those measurements in its record. The swap is phase B of the check pass, with the same lock, skip rules, temp naming, and cleanup, not a second pipeline.
- The hook milestone owns the session-start launch in `hooks/*.json`, the detached launch in front of the check's entry point, and the user-facing hook description. It does not change the pass.

The builder creates the copy in the new format from milestone 3's schema file, the same path a new warehouse takes. ### Run that copy under the writer flock with a time limit, first as a recorded rehearsal and later as a hard-link swap, and skip when the file is not ready
- Done: An internal engine entry point, which the user guide does not list, runs one pass in its own process under the writer flock. Each run records its outcome in one check record under the stockroom home and fsyncs it. Every run starts only when the file is old, checkpointed, and has no wal.
    - **Phase A** runs when the record holds no result for this check version. It builds and verifies a temp file and deletes it. It records `rehearsed` with the builder's measurements, free disk at the start, how long the pass held the lock, and the check version.
    - **Phase B** runs at a later session start, at least one day after a `rehearsed` record of the same check version. It builds and verifies a new temp file from the warehouse as it is that day, then hard-links the original to the backup name doctor reports. It fsyncs the new file and its directory, replaces the live path with that verified temp file, and records `swapped`. The original's SHA-256 before the swap equals the backup's SHA-256 after it.

  Swapped, mismatch, already new, a crash, and an overrun are final, and later runs do nothing; `rehearsed` is not final. Before it builds, the pass writes a started entry with its phase, start time, and time limit, so a crash or an overrun leaves that entry for doctor to show. Every pass takes the lock, without waiting, before it reads the record or deletes anything. A pass that cannot take the lock reads nothing, deletes nothing, and writes nothing, so it never overwrites a final result or deletes a running pass's temp file. Only the pass that holds the lock writes the record, by writing a temp file and renaming it into place. Each of these skips and leaves the original untouched: low disk, a wal, a busy flock, a read-only filesystem, no warehouse yet, and a warehouse below the format boundary (milestone 3's constant). There is no copy-then-delete fallback. A filesystem that refuses hard links is out of scope (see invariants), and because the link comes before the replace, a failed link never replaces the file. The low-disk test uses doctor's live-size estimate, not the original's file size. At the time limit the process ends itself, for example with `signal.alarm` and its default action, so the OS releases the flock and a waiting writer waits no longer than the limit. A test proves the limit ends a stuck pass and frees the lock. Under the lock, a leftover temp file is deleted even when the record is final. Cleanup never touches the original or a backup, and no code path deletes either. A skipped check does not make `open_current()` readers see the schema as behind head. Doctor shows the record's last outcome, including a skip reason, its measurements, and the record's path as one line in the storage section. Deleting that file runs the check again from phase A. Doctor shows a started entry that is still inside its time limit as running, not as a crash. Fault injection keeps `warehouse.duckdb` openable as either the original or the verified new file, with no data file lost, at each of these points: during create, build, and verification, after the hard link, and after the replace. "Already new" means the newest storage tag and zstd on both columns, read from the data segments in the file (see invariants), not the tag alone. Docs say how to roll back by renaming the backup, and that stockroom will not delete it. Tests use warehouses made in the old storage format on purpose. No hook or other shipped code starts the pass yet. A skip retries at the next session start and has no error state of its own (operator, 2026-10-22). If this milestone is classified larger than Level 3, split it into a rehearsal milestone and a swap milestone. Each stays dormant until milestone 7.
- Risks: Readers, the dashboard, doctor, ingest, embed, and the nightly job never start this. Phase B must copy the warehouse as it is that day, not replay the rehearsal's deleted temp file, because rows written since the rehearsal exist only in the old file. Readers that already have the old file open keep that inode until they reopen. Writers take the flock with a blocking call, so the time limit is the only bound on how long the nightly job, ingest, embed, or a migrating reader waits behind the pass. An interrupt may take effect only when the running statement ends (measured for `CREATE INDEX` on 1.5.4 and 2.0.0), so the limit must end the process, not interrupt the query. Nothing in the process may install a handler that stops the alarm from ending it. Only the entry point's own process sets the alarm, so a test that runs the pass in-process cannot leave an alarm that kills a `pytest-xdist` worker. The work machine's original is 88 GB without 88 GB free, so a low-disk test on the original's size would skip there forever. Several session starts at once are normal, for example when Cursor restores windows at login, so several passes can start together. A `v2.0.0+` file without zstd, from branch testing or from a release made before the new-file milestone shipped, is still copied. The kill switch is a release that changes the check version and keeps phase B off.
